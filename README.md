# HBS حلول الغد

مصدر موقع HBS وبوابة العملاء ومساحة المكتب، مع خادم API والحزم المشتركة اللازمة لهما. هذا المستودع يضم الشيفرة فقط، ولا يتضمن بيانات العملاء أو قاعدة البيانات أو ملفات الأسرار أو تطبيق الهاتف والفيديو.

## بنية المشروع
- artifacts/hbs-solutions: واجهة React وVite.
- artifacts/api-server: خادم Express وواجهات API.
- lib/db: مخطط قاعدة البيانات.
- lib/api-spec: تعريف OpenAPI ومولّد العميل.
- lib/api-client-react وlib/api-zod: الشيفرة المولّدة اللازمة للتشغيل.
- lib/integrations-*: موصلات الذكاء الاصطناعي المستخدمة في الخادم.

## الإعداد
استخدم Node.js 24 وpnpm. شغّل pnpm install، ثم pnpm --filter @workspace/api-spec run codegen عند تغيير تعريف API، وبعدها pnpm run typecheck وpnpm test. يشغّل GitHub Actions الفحوص نفسها مع بناء الواجهة والخادم على كل طلب سحب.

اضبط متغيرات التشغيل اللازمة من ملف .env.example في بيئة الاستضافة الآمنة، دون رفع قيمها إلى Git. يحتاج الموقع مساري /api و/api/__clerk إلى خادم API؛ إعداد توجيه المسارات في Replit يتم خارج هذا المستودع. يحتاج بناء الواجهة إلى PORT وBASE_PATH (مثال: PORT=5173 BASE_PATH=/ pnpm --filter @workspace/hbs-solutions run build). شغّل خادم API مع PORT منفصل. لا تنقل أو تستبدل قاعدة إنتاج بمجرد استيراد المصدر.

رفع الشيفرة إلى GitHub لا ينشر hrhbs.com تلقائيًا ولا يغيّر إعدادات موفّر تسجيل الدخول في Clerk.

## صلاحيات المكتب
- **المالك:** صاحب البريد المعتمد في HBS_OFFICE_EMAIL بعد تأكيده. يُنشأ سجله تلقائيًا عند أول دخول. يدير فريق المكتب من «فريق المكتب»، ويطّلع على «سجل التدقيق»، ويستورد الأرشيف القديم.
- **الموظف:** يضيفه المالك ببريده، بشرط أن يكون قد أنشأ حسابًا وأكّد بريده. يدير طلبات العملاء واستفساراتهم وطلبات التسجيل. تسقط صلاحيته فور إزالته، أو خلال دقيقة إذا أُلغي تأكيد بريده.
- **سجل التدقيق:** يُحفظ كل إجراء للمكتب (تحديث طلب، رد على استفسار، مراجعة تسجيل، استيراد أرشيف، إضافة موظف أو إزالته) مع التغيير نفسه في المعاملة ذاتها.

## ميزات التشغيل
- **إسناد الطلبات:** يختار المكتب مسؤولًا من الفريق وموعد إنجاز لكل طلب، ويصل للمسؤول بريد بذلك. في قائمة الطلبات فلتر «المسندة إليّ» و«المتأخرة فقط» وترتيب «الأقرب موعدًا».
- **الحالات:** تم الاستلام، قيد المراجعة، بانتظار العميل، تم الرفع للجهة، بانتظار السداد، مكتملة.
- **الأسعار والمتطلبات** (المالك، /office/catalog): أتعاب كل خدمة ومدتها والرسوم الحكومية والمستندات المطلوبة. لا يظهر للعملاء إلا ما يُنشر، في دليل الخدمات وصفحة الطلب الجديد.
- **الفواتير:** يصدرها المكتب على الطلب مع ضريبة 15% محسوبة وقت الإصدار، ويسجل السداد يدويًا أو يدفع العميل إلكترونيًا عبر صفحة ميسّر (مدى، البطاقات، Apple Pay) عند ضبط MOYASAR_SECRET_KEY. لا يُعتمد السداد الإلكتروني إلا بعد جلب الفاتورة من ميسّر ومطابقة المبلغ والعملة. لاستقبال إشعارات ميسّر: أضف Webhook إلى https://hrhbs.com/api/payments/moyasar/webhook مع نفس قيمة MOYASAR_WEBHOOK_SECRET. الفاتورة المطبوعة «فاتورة ضريبية مبسطة» وليست ربطًا بالمرحلة الثانية من «فاتورة» (ZATCA)؛ ذلك يحتاج تكاملًا منفصلًا.
- **تنبيهات الوثائق:** يضيف العميل (أو المكتب من صفحة الطلب) تاريخ انتهاء الإقامة أو الجواز أو السجل التجاري، فيصله بريد قبل الانتهاء بـ30 ثم 7 ثم يوم واحد (بتوقيت الرياض). يرى المكتب الوثائق القريبة من الانتهاء في /office/reminders.
- **القراءة الآلية للمستند:** زر في مستندات الطلب بلوحة المكتب يقرأ نوع الوثيقة وتاريخ انتهائها بالذكاء الاصطناعي، ثم يراجعها الموظف قبل حفظ التنبيه. كل قراءة تُسجَّل في سجل التدقيق.
- **واتساب:** يختار العميل من «الإشعارات» استلام رسائل واتساب برقم جوال سعودي. تُرسل عبر WhatsApp Business Cloud API بقالب معتمد من Meta فيه متغير واحد للنص، عند ضبط متغيرات WHATSAPP_*. دون ذلك تبقى الرسائل بالبريد فقط.
- **التقييم والتقارير:** يقيّم العميل الطلب المكتمل مرة واحدة. يرى المالك في /office/reports الطلبات والإنجاز ومتوسط مدته وأداء الفريق والتقييمات والمحصّل والفواتير المعلقة.

## قاعدة البيانات
تُدار تغييرات المخطط بملفات ترحيل في lib/db/migrations بدل drizzle-kit push.

- **تغيير المخطط:** عدّل ملفات lib/db/src/schema، ثم شغّل pnpm --filter @workspace/db run generate وراجع ملف SQL الناتج وارفعه مع التعديل. يفشل CI إذا تغيّر المخطط دون ملف ترحيل.
- **قاعدة جديدة فارغة:** شغّل pnpm --filter @workspace/db run migrate.
- **قاعدة موجودة أُنشئت سابقًا بـ push (مثل قاعدة الإنتاج الحالية)، مرة واحدة فقط:**
  1. خذ نسخة احتياطية من القاعدة، وجرّب الخطوات التالية أولًا على نسخة منها.
  2. تأكد أن الحالات والتصنيفات ضمن القيم المسموحة، وإلا فسيفشل الترحيل 0001 كاملًا دون أن يغيّر شيئًا. يجب أن يعيد هذا الاستعلام صفرًا:
     select (select count(*) from hbs_service_requests where status not in ('received','reviewing','waiting_on_customer','completed') or category not in ('passports','labor','business','other')) + (select count(*) from hbs_inquiries where status not in ('open','answered'));
  3. شغّل pnpm --filter @workspace/db run baseline لتسجيل المخطط الحالي كأنه مطبّق. السكربت يرفض العمل على قاعدة فارغة أو ناقصة الجداول، وتكراره آمن.
  4. شغّل pnpm --filter @workspace/db run migrate لتطبيق ما بعده.

  تشغيل migrate على قاعدة موجودة قبل baseline يفشل دون أن يغيّر شيئًا.
- **الأمر adopt** لقاعدة أُنشئت بـ push: يقارنها بالمخطط حتى الترحيل 0003 فقط (lib/db/scripts/adopt-schema.json) ويسجّل 0000-0003 كمطبّقة. الترحيلات اللاحقة (مثل 0004) يطبّقها migrate بعد ذلك، فبعد adopt -- --apply يطبّق migrate الترحيل 0004 مرة واحدة.
- **الأمر push** مخصص لقواعد التطوير المحلية فقط، ولا يُستخدم على الإنتاج.
- **اختبارات الخادم مع قاعدة البيانات:** ضع TEST_DATABASE_URL لقاعدة اختبار مرحّلة قبل pnpm test. الاختبار يفرّغ جداول المكتب فيها، فلا تستخدم قاعدة حقيقية.
