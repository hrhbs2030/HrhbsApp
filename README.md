# HBS حلول الغد

مصدر موقع HBS وبوابة العملاء ومساحة المكتب، مع خادم API والحزم المشتركة اللازمة لهما. هذا المستودع يضم الشيفرة فقط، ولا يتضمن بيانات العملاء أو قاعدة البيانات أو ملفات الأسرار أو تطبيق الهاتف القديم.

دليل التشغيل (النشر، الأسرار، المهام الدورية، الاحتفاظ بالبيانات، النسخ الاحتياطي، التراجع) في [docs/RUNBOOK.md](docs/RUNBOOK.md). تاريخ إعادة التصميم وقراراتها في [docs/REDESIGN.md](docs/REDESIGN.md).

## بنية المشروع
- artifacts/hbs-solutions: واجهة React وVite (الموقع العام المُسبق التصيير، بوابة العميل، مساحة المكتب)، مع خادم ملفات ثابتة للإنتاج server.mjs.
- artifacts/api-server: خادم Express وواجهات API والمهام الدورية.
- lib/db: مخطط قاعدة البيانات وملفات الترحيل 0000–0013.
- lib/api-spec: تعريف OpenAPI ومولّد العميل. lib/api-client-react وlib/api-zod: الشيفرة المولّدة منه.
- lib/integrations-*: موصلات الذكاء الاصطناعي المستخدمة في الخادم.
- scripts: مشغّل الاختبارات وحراس قاعدة الاختبار وسكربتات الصيانة.

## الإعداد
استخدم Node.js 24 وpnpm. شغّل pnpm install، ثم pnpm --filter @workspace/api-spec run codegen عند تغيير تعريف API، وبعدها pnpm run typecheck وpnpm test. يشغّل GitHub Actions الفحوص نفسها مع بناء الواجهة والخادم على كل طلب سحب، ويفشل إذا تغيّر تعريف API دون إعادة التوليد أو تغيّر المخطط دون ملف ترحيل.

متغيرات التشغيل مُعدّدة بأسمائها (دون قيم) في artifacts/api-server/.env.example وartifacts/hbs-solutions/.env.example، وجدولها الكامل في قسم «متغيرات البيئة» أدناه. تُضبط في مدير الأسرار لدى المستضيف ولا تُرفع قيمها إلى Git.

يحتاج الموقع مساري /api و/api/__clerk إلى خادم API؛ إعداد توجيه المسارات يتم خارج هذا المستودع. يحتاج بناء الواجهة إلى PORT وBASE_PATH (مثال: PORT=5173 BASE_PATH=/ pnpm --filter @workspace/hbs-solutions run build). شغّل خادم API مع PORT منفصل. رفع الشيفرة إلى GitHub لا ينشر hrhbs.com تلقائيًا ولا يغيّر إعدادات Clerk.

## الحسابات والصلاحيات

### فريق المكتب
- **المالك:** صاحب البريد المعتمد في HBS_OFFICE_EMAIL بعد تأكيده. يُنشأ سجله تلقائيًا عند أول دخول. يدير فريق المكتب والأسعار والخطط والقواعد، ويطّلع على التقارير وسجل التدقيق، ويستورد الأرشيف القديم.
- **الموظف:** يضيفه المالك ببريده بشرط أن يكون قد أنشأ حسابًا وأكّد بريده. يدير الطلبات والاستفسارات وطلبات التسجيل والرسائل وملفات العملاء. تسقط صلاحيته فور إزالته، أو خلال دقيقة إذا أُلغي تأكيد بريده.
- **سجل التدقيق:** كل إجراء للمكتب يُحفظ مع التغيير نفسه في المعاملة ذاتها، ويُعرض للمالك في /office/audit.

### العملاء
يسجّل العميل حسابًا عبر Clerk ثم يقدّم طلب تسجيل بالبريد المؤكّد ورقم الجوال، ويراجعه المكتب. بعد الاعتماد تفتح له لوحة التحكم والطلبات والاستفسارات والرسائل والوثائق وملف المنشأة والإعدادات.

### أعضاء المنشأة والتصرف باسمها
يدعو مالك المنشأة أعضاء بالبريد (حتى 10 أعضاء) بأحد الأدوار hr أو finance أو viewer، ويقبل العضو الدعوة بمجرد تسجيل دخوله بالبريد نفسه. يتصرف العضو **باسم المنشأة** لا باسمه:
- كل مسارات بيانات العميل (الطلبات، عروض الأسعار، قوائم المستندات، المرفقات، الفواتير، الاستفسارات، الرسائل، تنبيهات الوثائق، ملف المنشأة، ملخص اللوحة) تُقرأ وتُكتب على حساب مالك المنشأة، فيرى العضو ما يراه المالك ويظهر ما ينشئه في قائمة المالك وفي ملف العميل لدى المكتب.
- المسارات الشخصية تبقى على حساب العضو نفسه: إعدادات /settings، توثيق رقم واتساب، تفضيلات الإشعارات، اشتراكات الدفع الفوري (push)، ومغادرة العضوية.
- **owner** و**hr**: كل الإجراءات. **finance**: يقرأ كل شيء ويدفع الفواتير ويحدّث حالتها، ولا ينشئ طلبات أو استفسارات أو رسائل. **viewer**: قراءة فقط؛ أي كتابة تُرفض برسالة عربية.
- يعيد GET /portal/me الحقلين companyRole وactingFor، وتُظهر البوابة شارة «تتصرف باسم منشأة …» في الشريط العلوي، وتُخفي أزرار الإنشاء والتعديل عن viewer وتُبقي لـfinance أزرار السداد فقط.
- الطلب الذي ينشئه عضو يحمل created_by وsource = member، ويظهر للمكتب والمالك باسم من أنشأه.

## الطلبات والخدمات
- **دليل الخدمات** في /services مع بحث عربي يتجاهل الهمزات والتشكيل، ونتائج مباشرة تحت حقل البحث على الجوال. صفحة كل خدمة تبدأ الطلب واسم الخدمة معبأ.
- **الطلب الجديد:** نموذج من ثلاث خطوات (المجال، الخدمة والتفاصيل، المراجعة) مع رقم مرجعي، ورفع مستندات اختياري (حتى 10 ملفات، 10 ميغابايت للملف)، وربط الطلب بموظف أو ترخيص من ملف المنشأة، أو بعدة موظفين (حتى 50) لخدمات العمل والجوازات مع تتبّع لكل موظف. الإرسال المكرر محمي بمعرّف clientRequestId.
- **الحالات:** تم الاستلام، قيد المراجعة، بانتظار العميل، تم الرفع للجهة، بانتظار السداد، مكتملة. يرى العميل «سجل الحالة» لكل طلب، ويقيّم الطلب المكتمل مرة واحدة.
- **عروض الأسعار:** يرسل المكتب عرض سعر على الطلب فينتقل إلى «بانتظار العميل»؛ قبول العميل يصدر الفاتورة وينقل الطلب إلى «بانتظار السداد»، ورفضه يسجّل السبب في محادثة الطلب.
- **قوائم المستندات المطلوبة:** تُنسخ من بطاقة الخدمة المنشورة إلى الطلب، ويربط العميل ملفًا بكل بند، ويعود الطلب من «بانتظار العميل» إلى «قيد المراجعة» عند اكتمالها.
- **المستندات:** رابط رفع موقّع ثم نسخة مفحوصة في التخزين الخاص؛ تنزيلات المكتب وحذفه مسجّلة في التدقيق. القراءة الآلية للمستند (نوع الوثيقة وتاريخ انتهائها) تقترح تنبيهًا يراجعه الموظف قبل الحفظ.
- **الاستفسارات:** محادثة بين العميل والمكتب، ويُجيب المساعد «أم مشعل» عن أسئلة استخدام البوابة من المعلومات المعتمدة فقط ولا ينفّذ معاملات.
- **التصدير:** جداول الطلبات والموظفين والتراخيص تُنزَّل Excel أو تُطبع (PDF من المتصفح) بتوقيت الرياض.

## مساحة المكتب
- **قائمة الطلبات** كلوحة أو جدول، مع فلاتر «المسندة إليّ» و«المتأخرة فقط» و«بانتظار ردّنا» وترتيب «الأقرب موعدًا»، وإسناد جماعي. صفحة الطلب الكاملة /office/requests/:id تتنقل بالاختصارات J وK وتحفظ بـS.
- **الإسناد والأتمتة:** مسؤول وموعد إنجاز لكل طلب مع بريد للمسؤول. في «الأسعار والمتطلبات» يحدد المالك لكل مجال مسؤولًا وعدد أيام الإنجاز فيُسند الطلب الجديد تلقائيًا. يعود الطلب من «بانتظار العميل» إلى «قيد المراجعة» عندما يكتب العميل أو يرفع مستندًا، ومن «بانتظار السداد» عند تسوية آخر فاتورة مفتوحة، باسم «أتمتة النظام».
- **إدخال طلب للعميل:** من ملف العميل زر «إنشاء طلب للعميل» يستدعي POST /office/customers/{userId}/service-requests (الخدمة والمجال والوصف ورقم التواصل اختياريًا وموضوع الطلب). يُحفظ الطلب بمصدر office وباسم الموظف الذي أدخله، وتُطبّق عليه قواعد الإسناد نفسها، ويُسجَّل في التدقيق service_request.create_for_customer، ويصل العميل إشعار الاستلام المعتاد.
- **ملف العميل 360°** في /office/customers/:userId: الاسم والمنشأة وحالة التسجيل وتوثيق واتساب والاشتراك والفواتير غير المسددة وعدد الأعضاء وقائمتهم بأدوارهم والمحادثات غير المقروءة، مع روابط سريعة للرسائل وواتساب، وصفوف الطلبات تفتح صفحة الطلب مباشرة.
- **لوحة الأوامر:** Ctrl+K (أو ⌘K) وزر البحث في الشريط العلوي يفتحان لوحة أوامر واحدة في كل صفحات البوابة: للمكتب الصفحات والطلبات والعملاء، وللعميل الصفحات وطلباته واستفساراته.
- **الأسعار والمتطلبات** (المالك، /office/catalog): أتعاب كل خدمة ومدتها والرسوم الحكومية والمستندات المطلوبة. لا يظهر للعملاء إلا ما يُنشر.
- **التقارير** (المالك، /office/reports): الطلبات والإنجاز ومتوسط مدته وأداء الفريق والتقييمات والمحصّل والفواتير المعلقة.
- **طلبات التسجيل**، **فريق المكتب**، **سجل التدقيق** (آخر 200 سجل)، **الخطط**، **الاشتراكات**، **تنبيهات الوثائق** القريبة من الانتهاء في /office/reminders، و**الأرشيف القديم** (استيراد نسخة JSON من تطبيق الهاتف القديم إلى أرشيف مكتب مستقل؛ التفاصيل في artifacts/hbs-solutions/MIGRATION.md).
- **السجل التجاري:** استعلام «واثق» عن رقم السجل من ملف المنشأة (للعميل وللمكتب) عند ضبط WATHQ_API_KEY.

## الفواتير والسداد
- يصدر المكتب الفاتورة على الطلب مع ضريبة 15% محسوبة وقت الإصدار، ويسجل السداد يدويًا أو يدفع العميل إلكترونيًا عبر صفحة ميسّر (مدى، البطاقات، Apple Pay) عند ضبط MOYASAR_SECRET_KEY. اسم البائع ورقمه الضريبي من HBS_LEGAL_NAME وHBS_VAT_NUMBER. الفاتورة المطبوعة «فاتورة ضريبية مبسطة» وليست ربطًا بالمرحلة الثانية من «فاتورة» (ZATCA).
- **سلامة السداد:** إصدار الفاتورة محمي بمفتاح idempotency لكل طلب؛ صفحات الدفع المفتوحة تُحفظ في hbs_invoice_gateway_pages ولا يُعتمد السداد إلا بعد جلب الفاتورة من ميسّر ومطابقة المبلغ والعملة. إشعارات ميسّر تصل إلى /api/payments/moyasar/webhook بتوقيع MOYASAR_WEBHOOK_SECRET، ويراجع الخادم كل 30 دقيقة الصفحات المفتوحة فقط ليسجّل أي سداد فاته إشعاره، ويُغلق الصفحة عند السداد اليدوي أو الإلغاء.
- **تذكير الفواتير:** بريد للعميل بعد 3 أيام ثم 7 أيام من إصدار فاتورة غير مسددة.
- **الخطط والاشتراكات:** يعرّف المالك خططًا شهرية في /office/plans. يبدأ العميل (owner أو finance) الاشتراك من /company بعد مربع تأكيد يعرض الخطة والفاتورة الأولى وموعد التجديد؛ تُصدر الفاتورة الأولى فورًا وتتجدد شهريًا بتقويم الرياض. الاشتراك غير المسدد يصبح متأخرًا بعد 14 يومًا ويُلغى بعد 60 يومًا، ويعود نشطًا عند السداد. الخطة التي تشمل التجديد التلقائي تفتح طلب تجديد عند أول تنبيه لوثيقة موظف.

## ملف المنشأة والوثائق
- **ملف المنشأة** (للعميل في /company وللمكتب في /office/customers): بيانات المنشأة والموظفين والتراخيص. تعديلات المكتب مسجّلة في التدقيق. أرقام الهوية والجواز تُحفظ كاملة وتُعرض مخفية (آخر 4 أرقام)، وإظهارها من المكتب يُسجَّل.
- **الاستيراد من Excel** للموظفين والتراخيص مع نموذج جاهز، مطابقة الأعمدة بعناوينها العربية أو الإنجليزية، فحص كل الصفوف قبل الحفظ، حتى 500 صف في المرة.
- **تنبيهات الوثائق:** تواريخ انتهاء الإقامة والجواز ورخصة العمل والتراخيص (ومن صفحة /documents أو صفحة الطلب) تُنشئ تنبيهات قبل الانتهاء بـ30 ثم 7 ثم يوم واحد بتوقيت الرياض، عبر قناة الإشعارات. زر «اطلب التجديد» يفتح نموذج الطلب والخدمة والموظف معبآن.

## الإشعارات
- **مركز الإشعارات** في /notifications لكل من العميل والمكتب، مع عدّاد في الشريط العلوي، وتدفّق حي عبر SSE على /notifications/stream يعاود الاتصال تلقائيًا بتراجع متدرّج ويعود إلى الاستطلاع الدوري أثناء الانقطاع فقط. تنظيف المستمعين مضمون عند إغلاق الاتصال، وتُغلق التدفقات بسلاسة عند إيقاف الخادم.
- **خط أنابيب واحد** لكل حدث: أولوية محسوبة، دمج الأحداث المتكررة على الهدف نفسه، منع التكرار، ثم إرسال عبر القنوات المفعّلة: داخل التطبيق، البريد، الدفع الفوري للمتصفح، وواتساب للعملاء الموثّقين. الأنواع مُعدّدة في NotificationKind بالعقد.
- **التفضيلات** (/notifications): تفعيل البريد والدفع الفوري، ساعات هدوء، ملخص يومي بدل الإرسال الفوري، وكتم أنواع بعينها. ما يُحجز في ساعات الهدوء أو للملخص يُرسل بمهمة كل 10 دقائق، وأخطاء Clerk أثناء التحقق من موظفي المكتب لا تُسقط الصف بل تُعاد محاولته (بحد 3).
- **الدفع الفوري (Web Push):** يعمل عند ضبط VAPID_PUBLIC_KEY وVAPID_PRIVATE_KEY وVAPID_SUBJECT. يُقبل الاشتراك فقط عندما يكون عنوانه https ومضيفه إحدى خدمات الدفع المعروفة (Mozilla، FCM، Windows، Apple)، وبحد 5 اشتراكات لكل مستخدم (يُستبدل الأقدم). الإرسال بمهلة 10 ثوانٍ وبتوازٍ محدود لفريق المكتب، وتُحذف الاشتراكات الفاشلة بعد 30 يومًا.
- **الملخص الذكي** /notifications/brief: ما يحتاج انتباه المستخدم اليوم بروابط إلى صفحات حقيقية فقط (/documents للعميل، ومسارات /office/* للمكتب).
- **الاحتفاظ:** تُحذف الإشعارات المقروءة الأقدم من 180 يومًا يوميًا.

## المراسلات وواتساب
- **صندوق الرسائل** /messages (وللمكتب /office/messages): كل محادثات الطلبات والاستفسارات في مكان واحد مع علامات القراءة وعدّاد غير المقروء وتحديث حي. حدود: 20 رسالة لكل 10 دقائق لكل مرسل، و500 رسالة لكل محادثة. يصل الطرف الآخر إشعار بوصول رسالة دون نصها.
- **توثيق رقم واتساب:** يحفظ العميل رقم جوال سعودي في /settings ويفعّل الاستلام، ثم يطلب التوثيق فيحصل على نص تحدٍّ يرسله من جواله إلى رقم المكتب (OFFICE_WHATSAPP_NUMBER)؛ يطابقه الخادم عبر Webhook الوارد ويعلّم الرقم موثّقًا. تغيير الرقم يُسقط التوثيق. تعرض البوابة تنبيهًا عندما يكون الاستلام مفعّلًا والرقم غير موثّق.
- **روابط المتابعة:** من محادثة الطلب أو الاستفسار رابط يفتح واتساب على رقم المكتب والنص معبأ بالمرجع («طلب HBS-YYYY-NNNNN:» أو «استفسار #N:»). الرسائل الواردة التي تحمل المرجع تُسجَّل في المحادثة نفسها؛ ودونه تُضاف إلى الطلب المفتوح الوحيد أو تُفتح استفسارًا، ويصل المرسل رد تلقائي قصير.
- **صندوق واتساب المكتب** /office/whatsapp: الرسائل الواردة مع نية مقترحة وردود جاهزة؛ رد المكتب يُرسل عبر WhatsApp Business Cloud API ويُسجَّل في المحادثة. الأرقام غير المطابقة تظهر بمعاينة قصيرة.
- **الإرسال عبر واتساب** للعميل من المكتب يشترط رقمًا موثّقًا ومفعّلًا، ويُرسل بقالب معتمد من Meta فيه متغير واحد للنص عند ضبط WHATSAPP_ACCESS_TOKEN وWHATSAPP_PHONE_NUMBER_ID وWHATSAPP_TEMPLATE_NAME. الـWebhook الوارد على /api/webhooks/whatsapp يتحقق من WHATSAPP_VERIFY_TOKEN عند التسجيل ومن توقيع WHATSAPP_APP_SECRET لكل تسليم، ويرفض التسليم المكرر.
- **الاحتفاظ:** نصوص الرسائل الواردة تُحذف يوميًا بعد 90 يومًا من وصولها.

## الأمان والتشغيل
- حدود لكل عنوان IP على كل مسارات /api: 600 طلب في الدقيقة، 120 كتابة، و20 كتابة حساسة (التسجيل، إنشاء الطلبات والاستفسارات والرسائل، الدفع، الاستيراد، الأعضاء، الاشتراك، اشتراكات الدفع الفوري، ردود واتساب، توثيق رقم واتساب، إدخال المكتب للطلبات). استخراج المستندات بالذكاء الاصطناعي له حد أشد.
- CORS مقيّد بالأصول المعروفة وCORS_ALLOWED_ORIGINS. خادم الملفات الثابتة يرسل HSTS وCSP وX-Frame-Options وبقية الترويسات، ويخدم /.well-known/security.txt، ويرفض المسارات المخفية وملفات البناء.
- السجلات (pino) تحجب الترويسات الحساسة ولا تتضمن نصوص الرسائل أو الأرقام أو الرموز.
- عند SIGTERM أو SIGINT يغلق الخادم منفذ الاستماع، ويُنهي تدفقات SSE المفتوحة، ويترك المهمة الجارية تكتمل بحد 10 ثوانٍ، ثم يخرج.

## المهام الدورية
تبدأ كلها بعد الاستماع على المنفذ، وكل مهمة تعيد جدولة نفسها بعد اكتمالها (لا تداخل داخل العملية)، وتعتمد على مطالبات ذرّية في قاعدة البيانات فلا تتكرر الرسائل عند تشغيل أكثر من نسخة.

## قاعدة البيانات
تُدار تغييرات المخطط بملفات ترحيل في lib/db/migrations **فقط**؛ لا يُستخدم drizzle-kit push على الإنتاج ولا على قاعدة الاختبار المشتركة أبدًا.

- **تغيير المخطط:** عدّل lib/db/src/schema، ثم pnpm --filter @workspace/db run generate، وراجع ملف SQL الناتج وارفعه مع التعديل. يفشل CI إذا تغيّر المخطط دون ملف ترحيل، ويطبّق الترحيلات على قاعدة فارغة ويقارنها بـlib/db/scripts/expected-schema.json.
- **قاعدة جديدة فارغة:** pnpm --filter @workspace/db run migrate.
- **قاعدة قديمة أُنشئت بـpush:** نسخة احتياطية أولًا، ثم baseline (يسجّل المخطط الحالي كمطبّق) أو adopt (يقارن حتى الترحيل 0003 ويسجّل 0000–0003)، ثم migrate لما بعدها. migrate على قاعدة موجودة قبل baseline يفشل دون تغيير.
- **الأمر push** لقواعد التطوير المحلية المؤقتة فقط.

## الاختبارات والسكربتات
- pnpm test يشغّل scripts/run-tests.mjs all: فحوص الواجهة (سلامة الموقع، الصفحات، التباين المصيّر، البناء، خادم الإنتاج والتصيير المسبق) ثم فحوص الخادم، ثم فحوص قاعدة البيانات إذا ضُبط TEST_DATABASE_URL. أوضاعه: all وhbs وapi وapi-db.
- **فحوص قاعدة البيانات** تتطلب TEST_DATABASE_URL لقاعدة اختبار مرحّلة **مختلفة** عن DATABASE_URL؛ يتحقق scripts/test-db-env.mjs من هوية العنقود والقاعدة فعليًا قبل التشغيل ويرفض المطابقة. تفرّغ هذه الفحوص جداول المكتب والطلبات والإشعارات والرسائل والفواتير والاشتراكات، فلا تشر إلى قاعدة حقيقية. تُسجَّل كل مجموعة جديدة في artifacts/api-server/package.json وscripts/run-tests.mjs وقائمة dbCommands في scripts/db-command-guards.test.mjs.
- **scripts/run-isolated-persistence-tests.mjs:** ينشئ عنقود PostgreSQL مؤقتًا على منفذ محلي عشوائي، يطبّق ملفات SQL المرحّلة كما هي، يشغّل حرس القاعدة وفحوصها، ثم يحذف العنقود. يرفض العمل في الإنتاج. استخدمه عندما لا تتوفر قاعدة اختبار جاهزة.
- **scripts/post-merge.sh:** خطوة ما بعد الدمج في بيئة Replit: تثبيت التبعيات، توليد عميل API، ثم lib/db/scripts/verify-existing-schema.mjs الذي يتحقق **للقراءة فقط** من أن أعمدة آخر لقطة ترحيل وفهارسها موجودة في القاعدة دون أي كتابة. لا يستبدل migrate.
- **expected-schema:** يولّد أو يفحص (-- --check) شكل المخطط المتوقع بعد تطبيق كل الترحيلات؛ CI يفحصه.
- **artifacts/hbs-solutions/scripts/prerender.mjs:** بعد البناء يكتب routes.json وصفحات HTML مسبقة التصيير لكل مسار عام ونسخ .br/.gz للأصول.
- فحص التخزين الحقيقي test:attachment-storage يعمل فقط عند ضبط TEST_PRIVATE_OBJECT_DIR (بيئة Replit).
